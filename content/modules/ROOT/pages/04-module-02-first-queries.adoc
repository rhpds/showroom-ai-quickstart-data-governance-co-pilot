= Module 2: Your first governance-aware queries

Now that you understand the theory, it's time to experience agentic AI firsthand. You'll interact with the Data Governance Copilot using natural language and watch as it checks governance metadata and guides you toward compliant data sources while answering your questions about TradeNexus's e-commerce data.

In this module, you'll progress from simple database exploration to governance-aware analytics, building confidence in how the copilot keeps you safe while enabling self-service data access.

== Learning objectives

By the end of this module, you'll be able to:

* Access and use the Data Governance Copilot web interface
* Explore database schemas using natural language queries
* Inspect table structures and metadata without writing SQL
* Run analytics queries and observe the agentic loop in action
* Understand how governance metadata guides safe data discovery

== Exercise 1: Access the copilot and explore the database

Let's start by connecting to the copilot and asking it to describe what data is available.

=== Access the copilot interface

The Data Governance Copilot web interface is pre-deployed in your OpenShift environment.

. Open the Copilot UI in a new browser tab:
+
link:https://copilot-ui-user{guid}-data-gov.{openshift_cluster_ingress_domain}[Data Governance Copilot UI^]
+
Alternatively, you can navigate to your OpenShift cluster console and find the route under *Networking* → *Routes* in the `user{guid}-data-gov` project.

. You should see a clean chat interface similar to this:

image::Figure 1.png[Copilot Interface showing governance compliance notes,align="center",link=self,window=blank,width=600]

*Figure 1*: The copilot's main interface shows a conversational chat on the left and governance compliance notes on the right. When queries involve sensitive data, the copilot automatically highlights PII fields and certification status.

The interface includes:

* **Chat input** at the bottom for your natural language queries
* **Conversation area** displaying your questions and the copilot's responses
* **Toolbar buttons** at the top right for uploading governance policies and managing conversations

=== Your first query: database overview

Let's ask the copilot to describe what's in the database.

. In the chat input field, type:
+
[source,text]
----
Tell me about this database.
----

. Press Enter or click the Send button.

. Observe what happens:
+
TIP: Watch for status indicators showing tool calls like "Calling list_schemas()" and "Calling list_objects()". This is the agentic loop in action.

**What's happening behind the scenes:**

The copilot executes an agentic loop:

. **Iteration 1**: LLM decides to call `list_schemas()` to discover available schemas
. **Iteration 2**: Calls `list_objects(schema='public')` to enumerate tables in the main schema
. **Iteration 3**: May call `get_object_details()` for key tables to understand their structure
. **Final response**: Synthesizes findings into a natural language summary

**Expected response** (your model may vary slightly):

[source,text]
----
This is a PostgreSQL database containing TradeNexus e-commerce data. The database
includes:

• dim_customer: Core customer table (contains PII - restricted use)
• fact_orders: Order transaction history
• fact_order_payments: Payment details for orders
• v_rpt_customer_ltv_certified: [CERTIFIED] Gold-standard customer LTV view (PII-scrubbed)
• v_cust_ltv_agg_deprecated: [DEPRECATED] Old LTV calculation
• customer_master_deprecated: [DEPRECATED] Legacy customer table
• sales_rpt_v2: Sales report view (data before 2018)

The database includes certified views for safe analytics and deprecated objects
that should not be used for new reporting.
----

✓ You saw the copilot's response describing the TradeNexus database
✓ You observed tool call indicators showing the agentic loop iterations
✓ The response was in natural language, not raw table listings

== Exercise 3: Your first analytics query

Now let's query actual data -- and watch the copilot validate before executing.

=== Run a simple aggregation

. Ask:
+
[source,text]
----
How many customers do we have in each state?
----

. **Watch the agentic loop carefully**:
+
The copilot will:
+
. Call `list_objects()` to discover customer data sources
. Call `get_object_details('dim_customer')` → sees "CONTAINS PII, DO NOT USE FOR general BI"
. Call `get_object_details('v_rpt_customer_ltv_certified')` → sees "[CERTIFIED] Gold-standard, PII-scrubbed"
. Identify `customer_state` column in the certified view
. Generate SQL: `SELECT customer_state, COUNT(*) FROM v_rpt_customer_ltv_certified GROUP BY customer_state ORDER BY COUNT(*) DESC`
. Call `execute_sql()` with the generated query
. Return results with governance note

**Expected response**:

[source,text]
----
Customer distribution by state (using certified, PII-scrubbed data):

São Paulo (SP): 15,540 customers
Rio de Janeiro (RJ): 6,882 customers
Minas Gerais (MG): 5,773 customers
Rio Grande do Sul (RS): 5,466 customers
... (additional states)

Total: 96,096 unique customers across all states.

Note: Data sourced from v_rpt_customer_ltv_certified (certified for BI reporting,
PII-scrubbed). The dim_customer table was avoided because it contains PII and
is restricted to auth_service use only.
----

IMPORTANT: The copilot **checked governance metadata first**, discovered that dim_customer contains PII and is restricted, then recommended the certified, PII-scrubbed view instead. This is governance-aware guidance in action -- helping cooperative users make compliant choices.

=== Understanding the validation behavior

**Why the copilot didn't immediately generate SQL:**

A traditional chatbot might have guessed:

[source,sql]
----
-- Chatbot guess (might fail):
SELECT state, COUNT(*) FROM customers GROUP BY state
----

Problems with this approach:

* Table might be called `dim_customer`, not `customers`
* Column might be `customer_state`, not `state`
* Query fails if the guess is wrong

**The governance-aware agentic approach:**

. **Observe**: "I need to find customer data"
. **Decide**: "I'll list all tables and views first"
. **Act**: Call `list_objects()`
. **Learn**: "I see dim_customer, v_rpt_customer_ltv_certified, and deprecated objects"
. **Decide**: "I should check governance metadata before choosing"
. **Act**: Call `get_object_details('dim_customer')`
. **Learn**: "⚠️ CONTAINS PII, DO NOT USE FOR general BI"
. **Decide**: "I can't use dim_customer. Let me check the certified view"
. **Act**: Call `get_object_details('v_rpt_customer_ltv_certified')`
. **Learn**: "✓ [CERTIFIED] Gold-standard, PII-scrubbed for BI reporting"
. **Decide**: "Perfect! I'll use the certified view"
. **Act**: Call `execute_sql()` with query against v_rpt_customer_ltv_certified
. **Success**: Query runs safely using approved, PII-scrubbed data

=== Verify: Analytics query succeeded

✓ The copilot found the correct table and column names
✓ SQL was generated accurately without errors
✓ Results were presented in a readable format
✓ You didn't write any SQL yourself

== Exercise 4: Governance metadata inspection

Now let's see how governance policies are embedded in the database and how the copilot reads them.

=== Inspect governance metadata

The copilot can read governance annotations stored as PostgreSQL comments on tables and columns.

. Query:
+
[source,text]
----
Show me all the governance metadata for customer data sources.
----

. The copilot will:
+
* Call `list_objects()` to find customer-related tables and views
* Call `get_object_details()` for each to retrieve table/view comments
* Parse governance annotations embedded in comments
* Present metadata in a structured format

**Expected response**:

[source,text]
----
Governance metadata for customer data sources:

1. dim_customer (table) ⚠️ RESTRICTED
   Comment: "Core customer table. CONTAINS PII (PCI, address).
            DO NOT USE FOR general BI. Only for auth_service."

   Restrictions:
   • Contains PII (payment card info, addresses)
   • NOT approved for general BI or reporting
   • Limited to auth_service application use only

2. v_rpt_customer_ltv_certified (view) ✓ CERTIFIED FOR BI
   Comment: "[CERTIFIED] Gold-standard, PII-scrubbed view for all customer
            LTV reporting. Aggregated daily. Maintained by: Finance BI Team"

   Approval:
   • CERTIFIED for all BI and reporting use
   • PII-scrubbed (safe for general access)
   • Gold standard for customer lifetime value analysis
   • Maintained by Finance BI Team

3. v_cust_ltv_agg_deprecated (view) ⚠️ DEPRECATED
   Comment: "[DEPRECATED] Old LTV calculation. Only includes data before 2018.
            DEPRECATED as of Q3 2024. Do not use for new reporting.
            Use v_rpt_customer_ltv_certified instead."

   Status:
   • Deprecated as of Q3 2024
   • Only includes data before 2018 (incomplete)
   • Should NOT be used for new reports
   • Use v_rpt_customer_ltv_certified instead

4. customer_master_deprecated (table) ⚠️ DEPRECATED
   No comment (deprecated by table name)

RECOMMENDATION: Always use v_rpt_customer_ltv_certified for customer analysis.
It's the only certified, PII-scrubbed data source approved for general BI use.
----

=== Understanding governance-aware behavior

**How this solves TradeNexus's compliance challenge:**

. **Automated policy discovery**: Governance rules are stored in database metadata (comments) -- no separate policy management system needed
. **Pre-query validation**: Before executing queries, the copilot can check if the table is certified and safe to use
. **PII awareness**: The copilot knows which fields contain PII and can warn users or filter them automatically
. **Deprecated table avoidance**: The copilot can steer users away from deprecated tables toward current replacements

**What makes this governance-aware instead of just query generation:**

* **Traditional chatbot**: Generates SQL blindly, might query dim_customer (PII-restricted) or deprecated views without awareness
* **Data Governance Copilot**: Reads metadata first, detects PII restrictions, finds certified alternatives, recommends compliant data sources, then executes using the certified view -- guiding cooperative users toward good governance practices
